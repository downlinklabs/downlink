# Implementation Plan: Cluster API Gateway

**Branch**: `001-cluster-api-gateway` | **Date**: 2026-11-28 | **Spec**: [spec.md](./spec.md)

## Summary

A read + trigger HTTP API running as a separate binary and container image alongside the operator. It surfaces `SyntheticTest` and `SyntheticTestRun` resources to a presentation layer via an interface-abstracted `Store` so the data source can be swapped from the Kubernetes API to a hosted cloud data store without changing the API contract.

## Technical Context

**Language/Version**: Go 1.23 (new `api/` module matches operator module version)

**Module layout**: Go workspace (`go.work` at repo root) linking `operator/` and `api/`; `api/` imports CRD types from `operator/api/v1alpha1` and `WorkflowBuilder` from `operator/pkg/builder/`

**Primary Dependencies**: `net/http` (stdlib), `chi` router (lightweight idiomatic Go mux), `controller-runtime` cache-backed client (manager with no controllers — cache only)

**Storage**: Kubernetes API via dedicated controller-runtime cache (read path); `client.Client` for trigger write path

**Testing**: `net/http/httptest` for handler unit tests (per constitution Principle III); `envtest` for integration tests

**Target Platform**: Linux server, separate Deployment alongside the operator in the same namespace

**Project Type**: Standalone HTTP API service with its own controller-runtime manager (cache only), deployed as part of the same Helm chart as the operator

**Performance Goals**: Read responses under 200ms p95 on a cluster with up to 500 SyntheticTests (the cache-backed client makes this trivially achievable)

**Constraints**: Separate RBAC from the operator — API service account holds read access to `SyntheticTest`/`SyntheticTestRun` and write access to `Workflow`/`SyntheticTestRun` for the trigger path only; no operator-level privileges

**Scale/Scope**: Single cluster for v1; multi-cluster data shape required from day one per FR-008

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
|-----------|--------|-------|
| I. Kubernetes-Native | ✅ Pass | API reads CRDs via the existing controller-runtime client; no imperative state mutation |
| II. Workflow Delegation | ✅ Pass | Trigger path calls `WorkflowBuilder.BuildWorkflow()` — no execution logic in handlers |
| III. Test-First | ✅ Pass | Handler unit tests (httptest) and integration tests (envtest) must be written before implementation |
| IV. GitOps Compatibility | ✅ Pass | API is read + trigger only; no CRD creation/mutation from the API layer |
| V. Observability by Default | ✅ Pass | The API surfaces existing metrics; it does not emit its own synthetic test metrics |
| Single Responsibility | ✅ Pass | `Store` owns data access; handlers own HTTP shape; server owns routing and auth |
| Dependency Inversion | ✅ Pass | Handlers depend on `Store` interface, not on `k8sStore` concrete type |

**Post-design re-check**: No violations found. The `api/` binary is strictly additive — it only reads CRDs and submits Workflows/SyntheticTestRuns. The operator's reconciliation loop is unaffected.

**Structure Decision**: Separate binary and image. `api/` runs its own controller-runtime manager configured for cache-only use (no reconcilers). `WorkflowBuilder` moves from `operator/internal/controller/` to `operator/pkg/builder/` so both modules can import it without violating Go's `internal/` package restriction.
